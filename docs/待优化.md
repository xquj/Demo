\# 项目结构待优化项（全量清单）



> 范围：当前仓库代码与资源结构（`scripts/`、`scenes/`、`data/`、`docs/`、资源目录）。



\## P0（高优先级，先处理）



1\. \*\*状态写入口仍不唯一，存在并行写状态风险\*\*

&nbsp;  - `GameSense3D` 内既有 `\_switch\_state`，也在过渡处理函数里直接改 `global.current\_state`。

&nbsp;  - 交互脚本也可直接驱动状态切换（`global.game\_sense.\_switch\_state(...)`）。

&nbsp;  - 建议：增加统一状态门面（带 guard + 日志），禁止外部脚本直接写状态。  



2\. \*\*活跃玩家轮转公式可读性低（1v1 场景建议显式化）\*\*

&nbsp;  - 当前 `\_update\_player\_activity()` 同时混用了 `players\_size` 与 `% 2` 公式。

&nbsp;  - 在本项目固定 1v1 的前提下，建议改为“显式双人轮转逻辑”（如 team 1 / team 2 交替），减少误判和维护成本。  



3\. \*\*`global` 同时承担“运行数据 + 场景节点引用”，耦合过高\*\*

&nbsp;  - 目前 `global` 保存回合数据，也保存 Camera/Label/Desk 等场景节点引用。

&nbsp;  - 建议：拆为 `MatchState`（纯数据）与 `SceneRefs`（节点缓存）两个模块。  



4\. \*\*卡牌状态脚本仍承担业务写回，规则与表现未彻底分离\*\*

&nbsp;  - 例如 `SelectingState.exit()` 里直接做回合推进、卡牌归属写回。

&nbsp;  - 建议：状态脚本只保留视觉行为，业务变更下沉到命令/领域层。  



5\. \*\*状态切换依赖 `load(...)` 动态加载脚本，频繁 I/O 与弱类型\*\*

&nbsp;  - 多个状态脚本通过 `transition\_to(load("..."))` 切换。

&nbsp;  - 建议：预加载状态脚本常量或状态注册表，减少动态加载与路径错误风险。  



\## P1（中优先级，提升可维护性）



6\. \*\*命名风格不统一（camelCase 与 snake\_case 混用）\*\*

&nbsp;  - `waitingGroup`、`hand\_cards` 并存。

&nbsp;  - 建议：统一字段命名规范（推荐 snake\_case）。



7\. \*\*入口场景脚本存在空壳逻辑与遗留模板代码\*\*

&nbsp;  - `node\_2d.gd` 仍保留 `pass # Replace with function body`。

&nbsp;  - 建议：删除无效 `\_ready/\_process`，只保留实际入口逻辑。



8\. \*\*`end\_combo\_button.gd` 含无效生命周期函数与弱初始化\*\*

&nbsp;  - `\_ready/\_process` 空实现；`is\_entered` 未显式初始化。

&nbsp;  - 建议：移除空函数、显式默认值、补类型与注释。



9\. \*\*交互层仍暴露内部接口（调用 `\_switch\_state` 私有方法）\*\*

&nbsp;  - 按钮脚本直接调用 `global.game\_sense.\_switch\_state(...)`。

&nbsp;  - 建议：提供公开 facade 方法，隐藏内部状态机细节。



10\. \*\*按钮逻辑分散，回合推进策略不集中\*\*

&nbsp;   - `end\_waiting\_button.gd` 与 `end\_combo\_button.gd` 各自修改流程变量。

&nbsp;   - 建议：统一到 `TurnCoordinator`/`BattleFacade`，UI 只发意图命令。



11\. \*\*`global` 静态可变数据过多，不利测试与并发场景隔离\*\*

&nbsp;   - 当前大量 `static var` 直接被全项目读写。

&nbsp;   - 建议：改为实例化状态容器 + 依赖注入，便于单元测试。



12\. \*\*玩家模型职责偏胖，领域对象与流程对象未分层\*\*

&nbsp;   - `PlayerEntity` 同时包含属性与流程入口 `process()`。

&nbsp;   - 建议：拆分数据对象（PlayerState）与行为协调器（PlayerController）。



13\. \*\*卡牌实例直接持有 `player` 引用，容易形成双向耦合\*\*

&nbsp;   - `Card\_Base` 里有 `player: PlayerEntity`，状态脚本频繁反向操作玩家集合。

&nbsp;   - 建议：用 `owner\_id` + 仓储查询替代直接对象引用。



14\. \*\*`GameSense3D` 体量过大（输入、UI、状态机、生成、动画全在一处）\*\*

&nbsp;   - 建议：拆分为 `BattleFacade`、`Presenter`、`TurnSystem`、`CardSpawnSystem`。



\## P2（低优先级，工程卫生与扩展性）



15\. \*\*资源目录命名拼写错误（`textrue`）且未规范化\*\*

&nbsp;   - 建议统一为 `texture` 并配套资源命名规范（家族/ID/用途）。



16\. \*\*入口场景路径使用裸字符串，缺少统一常量管理\*\*

&nbsp;   - `change\_scene\_to\_file("res://node\_3d.tscn")`。

&nbsp;   - 建议抽出常量或场景路由器。



17\. \*\*状态脚本中魔法数字较多，可读性与调参效率一般\*\*

&nbsp;   - 例如位置偏移、角度、动画时间均散落硬编码。

&nbsp;   - 建议集中到配置常量（或 Scriptable config）。



18\. \*\*文档中提出的分层方案尚未落地为目录结构\*\*

&nbsp;   - 目前仍无 `domain/application/presentation` 分层目录。

&nbsp;   - 建议按 `CARD\_ARCHITECTURE\_REFACTOR.md` 逐步迁移。



19\. \*\*卡牌配置校验尚未形成“导入前检查”流程\*\*

&nbsp;   - `CardFactory` 有运行时校验，但缺少离线 lint/CI 检查。

&nbsp;   - 建议增加 JSON schema 或启动前校验脚本。



20\. \*\*缺少结构性测试基线（状态流转/回合推进/卡牌归属）\*\*

&nbsp;   - 建议为核心流程补最小自动化用例（headless 或脚本级）。



\## 建议执行顺序



\- \*\*第 1 阶段（止血）\*\*：1, 2, 3, 4, 9（其中 2 按 1v1 固定规则收敛）

\- \*\*第 2 阶段（解耦）\*\*：10, 11, 12, 13, 14, 18

\- \*\*第 3 阶段（工程化）\*\*：5, 6, 7, 8, 15, 16, 17, 19, 20
